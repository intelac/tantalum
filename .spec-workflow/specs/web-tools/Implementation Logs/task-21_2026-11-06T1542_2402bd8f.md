# Implementation Log: Task 21

**Summary:** Follow-up to task 21: fixed a bug found in the parent's real-Claude demo on 8091. web_fetch returned "Could not fetch …: the connection failed." for every HTTPS URL that answered with a redirect, for example api-docs.deepseek.com 302, arxiv 303, and duckduckgo's cross-host 302.

Root cause, reproduced directly with the Egress client:
- For redirects and refused types, Fetcher.LimitedBody does not read the body. Its onSubscribe cancelled the subscription first and only then completed the body.
- HTTPS through the egress CONNECT tunnel negotiates HTTP/2 via ALPN. On HTTP/2 the JDK HttpClient fails the whole response when the subscription is cancelled before the body is done: IOException "Stream 1 cancelled".
- On HTTP/1.1, cancelling just closes the connection, so the plain-http FetcherIT never showed it.
- The same ordering broke the 5 MB cut and the image/PDF messages over HTTPS.

Fix: LimitedBody.stop(body) completes the body first, then cancels.

Regression test: new FetcherTlsIT (failsafe) runs an embedded Tomcat with TLS and an Http2Protocol upgrade on 127.0.0.1, using a self-signed EC certificate generated with keytool at test time. Only during Egress.start is the JVM default SSLContext set to trust that one certificate, then it is restored; production trust is unchanged. It checks:
- a same-host 302 and a 303;
- a cross-host 302 from 127.0.0.1 to localhost, which needs a new CONNECT;
- that the server really saw HTTP/2.0;
- that image/png gets its own message;
- that a 6 MB text/plain page stops at 5 MB.

All three tests failed before the fix and pass after it; FetcherIT is still green. The three public URLs were checked once by hand with the fixed Fetcher:
- deepseek 302 → 200 at .../news261017/;
- arxiv 303 → search.html → search.json 404, which is the site's real answer;
- duckduckgo → 200 at html.duckduckgo.com.
