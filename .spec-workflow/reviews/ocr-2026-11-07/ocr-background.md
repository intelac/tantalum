Tantalum is a multi-user, self-hosted agent runtime in Java 25 (records, sealed interfaces, virtual threads) with a React console. About 150 commits landed in the last week (local workspace tools on the user's computer, web fetch and a per-user headless browser, model picker, console i18n, Windows server support, waiting-for-answer runs, persistent logins and administrators, hook patches as appended system messages). We want a whole-codebase review with two concerns in mind:

1. Did the recent changes break the architecture?
   - Three layers with one dependency direction: tantalum-value (immutable records, events, commands, state; JDK only) <- tantalum-kernel (pure logic: transition table and hooks; no I/O, no clock, no threads) <- tantalum-shell (all I/O: Disruptor rings, journal, handlers, model clients, Spring web). tantalum-local holds tools that run on the user's computer and the connector message format and must not depend on shell or Spring. tantalum-connect is the connector program. tantalum-examples contains example plugins that may only use the public plugin API.
   - The kernel is a pure function: Kernel.step(state, event) -> decision. Every step and its result are written as one line of an append-only per-session JSONL journal before taking effect; restarts restore the recorded results instead of recomputing; replay of old journal lines must be byte-identical (old lines must still decode and re-encode identically). Hooks are pure functions; any I/O goes through "work" handled outside the kernel.
   - Plugins are called only through PluginGate, which enforces per-user switches. API keys come only from environment variables and never enter the journal, logs, SSE or the model context. Connector tokens are never logged. The server never reads or writes user files (only attachments). Web egress goes through a single Egress class that checks resolved addresses.
   - Shell packages depend in one direction (no cycles).

2. Is the new code "patch-like"? Flag: special-case flags threaded through many methods; copies of the same logic in two places (for example between the Claude and the OpenAI client, or between the kernel projection and the shell); nullable fields added only for backward compatibility without a clear owner; growing god classes (Engine, ApiController, RecordCodec, TantalumProperties); state records with many withX methods; comments that only make sense with the spec id; error handling that swallows failures; tests that assert implementation details instead of behavior.

Report concrete defects (correctness, concurrency, resource leaks, security) with the usual precision, and in addition report architecture violations and patch-like code with a short justification and a suggested direction. Do not report style nits or missing Javadoc. The code comments are in Chinese; that is intentional.
